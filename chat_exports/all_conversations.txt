১২. এখন coder-কে যে কাজটা দিতে হবে

আমি তাকে এই instruction-টাই দিতাম:

Stop polishing individual screens.

Rebuild the C-Link visual system around one canonical Work Reality.

There must be exactly one canonical WorkScene and one state model. Actor, sender, responder, supplier, employee, company, individual and counterparty must only receive different projections of the same underlying Work.

First-use must begin accountlessly. A user states a need through the chat composer. The compiler converts that language into Intent → Outcome → Need → Responsibility → Dependency → Capability → Commitment → Evidence → Action → Observation → Shared State.

The initial UI must not look like a dashboard or form. It must be a finite asymmetrical Living Mosaic where territories sacrifice space to let meaningful Work expand.

When a user taps a territory, it must expand in place. When they type, the mosaic must reorganize around the resulting Work. When a counterparty opens a C-Link, they must enter the same Work reality from their own perspective, not see a separate request page.

When the counterparty accepts, the Work must not become an invitation to join an application. The accepted responsibility must materialize directly inside that actor's own Work field.

Every state transition must alter spatial territory and motion, not merely text labels.

Conversation, commitment and evidence must bind to the same Work object.

Time travel must replay the same Work objects through historical states rather than opening separate history screens.

Delete or merge duplicate visual implementations. No route may render an obsolete mosaic, static recipient UI, dashboard-like substitute or legacy Pixi world.

Build and test desktop and mobile simultaneously.

Do not declare success from unit tests alone. Run the system as multiple real humans: anonymous initiator, anonymous counterparty, supplier, employee, manager, owner and downstream dependency. Perform the complete journey from natural-language Need → share → open → understand → respond → accept → responsibility appears → internal dependency emerges → downstream actor responds → commitment → evidence → fulfillment → replay.

At every step ask:

“Does the interface feel like the user has entered their own work, or does it feel like they are operating someone else's software?”

The target is the former.

If a visual decision conflicts with the Work Reality model, reject the visual decision.

Do not add new UI patterns to compensate for architectural confusion. Fix the canonical model instead.

Production readiness means the same canonical Work survives accountless entry, actor transition, counterparty transition, realtime state changes, reconnect, permission boundaries, evidence binding and temporal replay without changing identity or reality.

এইটাই এখন আসল direction।

আর তোমার screenshot দুটো দেখে আমার blunt verdict:

বর্তমান coder অনেকটা এগিয়েছে, কিন্তু এখনও “C-Link-এর visual language” বানায়নি। সে C-Link-এর বিভিন্ন state-এর UI বানিয়েছে।

আমি তাকে এই কথাগুলোই পাঠাতাম:

Stop treating child mosaic as a new screen. The parent mosaic must remain mounted and remain the spatial coordinate system.

On tap, do not replace ParentMosaic with ActorFocus/ChildMosaic. Keep the selected card in the parent mosaic and animate its existing rectangle from its current bounds to a larger rectangle. Other parent cards simultaneously animate to their sacrificed bounds.

Only after/in parallel with that geometry transition, mount the child mosaic inside the selected card's expanded bounds. The child mosaic must use the selected card's rectangle as its finite coordinate space, never the viewport.

No fixed, viewport-level 100vw/100vh, route replacement, or full-screen focus surface for nested mosaic.

The interaction must visually read as:

parent card → same card expands in place → neighbours compress → inner mosaic appears inside it

Not:

parent screen → child screen.

Use the actual before/after DOM bounds for GSAP FLIP/layout animation so the transition has spatial continuity.

Session: C-Link UI-এর “Interaction Architecture”

আমার মতে সবচেয়ে বড় ভুল হবে corkboard-টাকে একটা সুন্দর dashboard বানিয়ে ফেলা।

C-Link board dashboard না।

এটা হবে এমন একটা জায়গা যেখানে user অনুভব করবে:

“আমার পৃথিবীতে এখন কী ঘটছে, কী আটকে আছে, কে কী দায়িত্ব নিয়েছে, এবং কোন জিনিসটা সামনে এগোচ্ছে।”

অর্থাৎ board-এর visual hierarchy হবে state-driven, decorative নয়।

7. কিন্তু motion কখনো constant হবে না

17. সবচেয়ে বড় UI principle

আমি এটাকে C-Link-এর design law বানাতাম:

The user should never manage the system.
The user should manage reality through the system.

মানে user-এর কাজ:

না:

“task create করা”

না:

“workflow configure করা”

না:

“module select করা”

বরং:

“আমি কী ঘটাতে চাই?”

তারপর C-Link নিজে:

Need → Capability → Actor → Commitment → Execution → Evidence → Outcome

এগুলো organise করবে।

Session 4 — Corkboard-এর Spatial Grammar

আমার মতে board-এর সবচেয়ে গুরুত্বপূর্ণ rule হবে:

Board-এ জায়গা decoration নয়, meaning বহন করবে।

অর্থাৎ কোনো object কোথায় আছে সেটাই তার semantic state-এর অংশ।

1. Board-কে ৫টা permanent territory-তে ভাগ করি
┌─────────────────────────────────────────────────────┐
│                    NOW / PULSE                      │
│                                                     │
│   NEEDS                ACTIVE EXECUTION             │
│                                                     │
│   ○ Need A        ────────●───────────              │
│   ○ Need B                 │                         │
│                           │                         │
│                    COMMITMENT                       │
│                           │                         │
│                 ──────────●──────────               │
│                           │                         │
│                    COUNTERPARTY                      │
│                           │                         │
│                      OUTCOME                         │
│                                                     │
│              HISTORY / TIME RAIL                    │
└─────────────────────────────────────────────────────┘

কিন্তু এগুলো rigid columns হবে না।

এগুলো হবে soft spatial zones।

মানে corkboard-এর ওপর কোনো invisible grid আছে, কিন্তু user সেটা অনুভব করবে না।

User যেন মনে না করে:

“আমি একটা workflow diagram দেখছি।”

বরং:

“এই জিনিসটা কোথা থেকে শুরু হয়ে এখন কোথায় যাচ্ছে সেটা দেখছি।”
